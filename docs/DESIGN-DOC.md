# AI Agent Command Center — Design Document

Working title: Roundtable. Backend: Serverpod (Dart). Panel: Flutter/web. Hackathon: Serverpod Hackathon (BuilderBase), 5 weeks.

## 1. Problem and vision

Working with coding agents (e.g. Claude Code) today looks like this: SSH into a machine, terminal, manually watching the output, a GitHub PR as the only review interface. There's no single place to see what's happening, on which machine, and what exactly the agent changed.

This app is a command center: a developer registers their machines (laptop, VPS), which host agents — named, with an assigned role/specialty — assigns them tasks on a specific git repository, and watches the work live — streamed logs, a diff of the changes, the resulting PR — from one panel. They can leave feedback that goes back to the agent as another iteration.

## 2. Constraints from the hackathon rules

- The repository must be **self-contained** — everything needed to build and run the project must be in the repo. No install scripts hosted on an external, private URL as the only source.
- The app must be runnable **locally on the judge's machine** — a single command (`docker compose up`), with no requirement to spin up a separate VPS. The real scenario with a remote machine is shown in the demo video, but evaluation must be possible locally.
- Required: a text description of the features, build & run instructions, a demo video <2 min (YouTube/Vimeo, public, no third-party trademarks/music).
- Presentation quality is **not** scored separately — time should go into the product, not video production.

## 3. Architecture

Key decision: **the agent connects outbound to the central server**, not the other way around (analogous to GitHub Actions self-hosted runners / Jenkins agents). This means nothing needs to be exposed publicly on the agent's VPS — no NAT, firewall, or certificate issues.

```
Panel (Flutter/web)
      │  method calls + stream subscriptions
      ▼
Central server (Serverpod)
   ├─ database (projects, tasks, logs, questions)
   └─ streaming methods (Stream<T> over Model.db.watch())
      ▲
      │  outbound connection from the agent (token)
Agent runner (VPS / laptop)
      │  subprocess
      ▼
Claude Code (headless mode, --output-format stream-json)
      │
      ▼
GitHub repo (push branch, PR)
```

Serverpod streaming methods (`Stream` instead of `Future` on an endpoint) manage the WebSocket, reconnection, and authorization themselves. If the endpoint does `Model.db.watch(...)`, every change in the database automatically flows to all subscribed clients — no manual pub/sub, no Redis, no queues.

**`Machine` vs `Agent` distinction:** a machine is pure infrastructure (host, connection token). An agent is a persona living on a machine — it has a name, a role, a status. One machine can host multiple agents (1:n).

### 3.1 Communication protocol

Under the hood, Serverpod is plain HTTP + WebSocket, not some closed protocol: regular method calls (`Future`) are `POST /[endpoint]/[method]` with a JSON body (pure RPC), and streaming methods (`Stream`) go over WebSocket — **a single WS connection handles many concurrent streams at once** (multiplexed), with reconnection built into the generated client.

The agent runner is therefore written as a **Dart CLI app importing the generated `_client` package** — it gets exactly the same typed interface as the panel (`client.task.watchAssignedTasks(machineId)`, etc.), without writing its own HTTP/WS handling from scratch.

### 3.2 Frontend and repo structure

**Decision: we're sticking with Flutter** (it also compiles to web, so it satisfies "the panel is a web app"), not going with React/Next.js. This is a technical reason, not just a preference: Serverpod has no official TypeScript/JS client generator, and the streaming WebSocket protocol isn't documented as a public standard for consumption by non-Dart clients. React would mean building our own gateway (e.g. a server translating Serverpod's streaming to SSE) for exactly the feature that's the heart of the demo — a bad time trade-off for 5 weeks.

The repo structure isn't something we invent ourselves — it's the built-in, official scaffold generated by `serverpod create`/`serverpod quickstart`, a single Dart workspace:

```
my_project/
├── my_project_server/   # backend
├── my_project_client/   # GENERATED client, never edit by hand
├── my_project_flutter/  # panel (also compiles to web)
└── my_project_agent/    # CLI daemon, added by us, depends on my_project_client
```

The panel and the daemon on the VPS use the same generated type contract — changing an endpoint's signature produces a compile error in both places, instead of drifting apart only at runtime.

### 3.3 Panel architecture (flutter_bloc)

The panel is largely made of streams (logs, task status, machine metrics, plan-mode questions) — BLoC maps onto this naturally: a Cubit/Bloc wraps a Serverpod `Stream<T>` and emits successive states.

- **Cubits** (no events) wherever wrapping a single stream and exposing the latest state is enough: `MachineListCubit`, `AgentListCubit`, `MachineMetricCubit`.
- **Full Blocs** (with events) wherever several event sources need to be combined at once: `TaskDetailBloc` reacts simultaneously to the log stream, status changes, a possible plan-mode question, **and** user actions (cancel, feedback, answering a question).
- **A repository layer between the Bloc and the generated client** (`TaskRepository`, `MachineRepository`) — a Bloc never touches `client.*` directly. Easier to test/mock without a real server connection.

```dart
class TaskDetailBloc extends Bloc<TaskDetailEvent, TaskDetailState> {
  TaskDetailBloc(this._repo, int taskId) : super(TaskDetailInitial()) {
    on<TaskDetailSubscribed>((event, emit) async {
      await emit.forEach(
        _repo.watchTask(taskId),
        onData: (task) => state.copyWith(task: task),
      );
    });
  }
}
```

Rule of thumb to avoid boilerplate creep: **Cubit by default, Bloc only when there's genuinely more than one event source.**

## 4. Scope (MoSCoW)

### Must

| Feature | Notes |
|---|---|
| Adding a project (name, repo link) | |
| Configuring access to a private repo | token (see §6.5) |
| Adding a machine + registration token | token stored as a hash, shown to the dev only once — full handshake in §6.8 |
| Agent (daemon) install script | a file in the repo, not an external URL, installs a systemd service — §6.8 |
| Uninstall script | stops the service and revokes the token server-side — §6.8 |

| Default model and effort per agent | e.g. Adam (code review) → a stronger model + higher effort; Ana (development) → cheaper/faster — see §6.6 |
| Machine status (online/offline) | heartbeat + periodic Future Call detecting timeout — §6.8 |
| Claude Code authorization on the machine | Pro/Max subscription via `claude setup-token`, bootstrapped during install — §6.11 |
| Adding a task | prompt + assignment to a project/agent |
| Task execution by the agent | `native` mode, isolation via a git worktree per task — see §6.10 |
| Live agent status + live output | streaming methods |
| Viewing changes (diff) in the panel | the server fetches it via the GitHub API (`repoAccessToken` never reaches the panel) and returns the parsed result — see §6.7. Embedding the GitHub page in an iframe won't work (GitHub sends `X-Frame-Options: deny`) |
| Feedback → another iteration | **after** the PR is created, not before; continuation of the same Claude Code session (`--resume`) |
| Ability to stop/cancel a task | an agent can get stuck in a loop — without this, a live demo is defenseless; mechanics in §6.1 |
| Agent↔server authorization via token | not to be confused with user login (we're not doing that) |
| Handling `AskUserQuestion` from plan mode | full handling, not auto-rejection — `--permission-prompt-tool` + `TaskQuestion`, see §6.4 |
| Approving the plan or giving feedback on it | a gate on `ExitPlanMode`, not auto-approval — see §6.4 |
| Skipping planning for small tasks | `Task.skipPlanning` — saves Claude Code usage on trivial tasks |

### Should

- Task queueing on a single machine / for a single agent
- Agent health-check / heartbeat (distinguishing "crashed" from "not responding")
- Timeout for a stuck task
- A simple Kanban: backlog → in progress → review → done
- Viewing the full content of a changed file (not just the diff) — see §6.7
- Basic machine metrics in the dashboard: CPU/RAM as a current reading (snapshot) — see §6.9

### Could

- A richer Kanban (backlog → ready to pick up → assignee/schedule → review) — the plan-approval gate (§6.4) already covers the "plan → approval" core, this extends it with the remaining states
- Notifications when a task finishes
- Full task history per project (audit log)
- Statistics: execution time, % of merged PRs
- Automatic routing of a task to the best-fitting agent (based on role/task content)
- Saved prompt templates
- A budget limit (token cost per task/project)
- CI integration (test status in the panel)
- Commenting on specific diff lines
- A GitHub App instead of a PAT for repo access (see §6.5)
- A real-time CPU/RAM usage chart (history, not just a snapshot) — see §6.9
- `docker` execution mode per agent (dependency isolation, e.g. different Node versions between projects) — schema ready as of Must, implementation deferred — see §6.10
- Support for agent tools other than Claude Code (e.g. OpenCode, non-Anthropic models) — deliberately deferred; the MVP hard-codes Claude Code as the only tool, not via a "pluggable tool" abstraction

### Won't

- User login / registration
- A separate mobile app
- Support for repo hosts other than GitHub
- Team roles and permissions (multi-tenant, RBAC)
- Hard permission restrictions per agent role (e.g. blocking a frontend agent from touching the backend) — a role is prompt context, not a sandbox

### Design decisions worth remembering

- `tokenHash` / `repoAccessToken`, never raw secrets directly in code — always `scope=serverOnly`.
- `Machine` and `Agent` are separate entities: a machine = infrastructure, an agent = a persona (name, role, status). One machine → many agents.
- `Machine.status` (online/offline) and `Agent.status` (idle/waitingForResponse/busy) are deliberately two separate fields, not one shared one — otherwise it's easy to end up with an inconsistency like "agent online, but its machine is already dead." "Offline" exists only on `Machine`. `waitingForResponse` is purely cosmetic — the agent doesn't take a new task in this state either way, it's just a better UI signal than a generic "busy"; real support for multiple parallel tasks per agent stays in Should.
- `Task.agent` is optional — this opens the door to task queueing without a schema change.
- `MachineMetric` is a table that grows over time (a sample every few seconds) — it needs periodic cleanup of old entries (Future Call), otherwise it grows without bound. See §6.9.
- Execution isolation is a git worktree per task (MVP, no Docker), not a separate system user or a container. `docker` mode is a property of a single agent (`Agent.executionMode`), not a global decision — schema ready, implementation deferred. See §6.10.
- Editing and deleting `Project`/`Machine`/`Agent` are standard CRUD operations, assumed without a separate write-up. Two caveats for `Machine`/`Agent`: (1) deletion is blocked while it has non-terminal tasks; (2) deleting a `Machine` is blocked while `status == online` — see §6.8.
- Diffs/changes don't have their own table — the panel fetches the ready-made diff from the GitHub API on demand (we don't store it in the database), to avoid duplicating repo state.
- Diff in the panel ≠ a GitHub iframe. GitHub sends `X-Frame-Options: deny` on its pages — embedding won't work. Instead we fetch the raw text diff and color it ourselves (see §6.7).

## 6. Key flows

### 6.1 Task lifecycle

1. The dev creates a `Task` (project + agent + prompt, optionally `skipPlanning`) in the panel.
2. The daemon on the machine, subscribed to `watchAssignedTasks(machineId)` (not by `agentId` — one daemon serves all agents hosted on that machine), gets notified and checks which of its agents the task belongs to.
3. The daemon prepares an isolated working directory for this task — in the MVP via a git worktree, see §6.10 (authenticating with the project's token, see §6.5).
4. **If `skipPlanning = false` (default):** the daemon launches Claude Code in `--permission-mode plan`. `Agent.status → busy`, `Task.status → planning`. Any `AskUserQuestion` → `Task.status = waitingForAnswer`, `Agent.status → waitingForResponse` (see §6.4). Once planning finishes (`ExitPlanMode`) → `Task.status = planReady`, `Agent.status → waitingForResponse`, `Task.currentPlan` saved. The dev approves or gives feedback (a loop, see §6.4) — only after approval does `Task.status → running`, `Agent.status → busy`.
   **If `skipPlanning = true`:** the planning step is skipped entirely, the daemon goes straight to execution.
5. Execution: the daemon launches Claude Code as a subprocess "on behalf of" the assigned agent (the same session, `--resume`, if we planned earlier), with the prompt prefixed by the agent's role (see §6.6), `--permission-prompts none`. `Task.status → running`.
6. Output lands as a `TaskLogEntry`, the panel sees it live.
7. On completion: the daemon commits/pushes/opens a PR (**not** Claude Code — control over the commit format and the PR link stays with the daemon; a commit is only created **on a successfully completed run**, never mid-run). `Agent.status → idle`, `Task.status → awaitingReview`.
8. The dev sees the diff/PR in the panel.
9. The dev leaves feedback → a new `TaskFeedback` (`phase = review`) → the agent resumes the same Claude Code session via `--resume <claudeSessionId>`, continuing on the same branch. Prior commits/PR remain untouched regardless of what happens to this iteration.

**Cancelling mid-run:** besides listening for new tasks, the daemon also subscribes to `watchTask(taskId)` for whatever task it's currently running. A status change to `cancelled` (initiated by the dev in the panel) wakes this subscription — the daemon sends `SIGTERM` to the Claude Code subprocess and resets the worktree (`git reset --hard` + `git clean -fd`, see §6.10). Since a commit is only created after a successfully completed run, there's nothing to "roll back" — any earlier, already-pushed commits remain untouched.

### 6.2 Launching Claude Code (headless)

**Planning phase** (skipped when `Task.skipPlanning = true`):

```bash
claude -p "<role prefix> <task prompt>" \
  --output-format stream-json \
  --verbose \
  --include-partial-messages \
  --permission-mode plan \
  --permission-prompt-tool <local-mcp-tool> \
  ${agent.defaultModel != null ? '--model ${agent.defaultModel}' : ''} \
  ${agent.defaultEffort != null ? '--effort ${agent.defaultEffort}' : ''}
```

**Execution phase** (after the plan is approved, or immediately when `skipPlanning = true`; `--resume` if we planned earlier):

```bash
claude -p "<prompt, or empty if --resume>" \
  --output-format stream-json \
  --verbose \
  --include-partial-messages \
  --permission-prompts none \
  ${task.claudeSessionId != null ? '--resume ${task.claudeSessionId}' : ''} \
  ${agent.defaultModel != null ? '--model ${agent.defaultModel}' : ''} \
  ${agent.defaultEffort != null ? '--effort ${agent.defaultEffort}' : ''}
```

- `stream-json` = one JSON line per event (NDJSON), the daemon parses it as it arrives.
- Planning phase: `--permission-prompt-tool` intercepts `AskUserQuestion` and `ExitPlanMode` (see §6.4) instead of auto-rejecting them.
- Execution phase: `--permission-prompts none` = fully unattended mode.
- The final `result` message (of either phase) contains a `session_id`, which we store as `Task.claudeSessionId` — needed for `--resume` on the planning→execution transition and on feedback.

### 6.3 How logs reach the panel

After parsing each NDJSON line, the agent calls an ordinary Serverpod method (`taskEndpoint.appendLog(taskId, content)`), which stores a `TaskLogEntry`. The panel has `watchLogs(taskId)` open, built on `TaskLogEntry.db.watch()` — a database write automatically reaches every watching client, with no manual broadcast.

### 6.4 Handling plan mode: `AskUserQuestion` and the plan-approval gate (`ExitPlanMode`)

In `--permission-mode plan`, Claude Code analyzes the code without making changes and may: (a) ask a clarifying question (`AskUserQuestion`), (b) once planning is done, try to move to implementation (`ExitPlanMode`). Our `--permission-prompt-tool` intercepts **both** calls and handles them differently — neither is auto-approved:

**`AskUserQuestion` (a question with options):**
1. The tool creates a `TaskQuestion`, `Task.status = waitingForAnswer`.
2. The tool **blocks**, subscribing to `watchAnswer(questionId)` (a streaming method).
3. The panel renders the question with its options. The dev picks an answer → `answerQuestion(questionId, answer)` → wakes the blocked tool.
4. The tool returns the answer to Claude Code, planning continues.

**`ExitPlanMode` (plan ready, requesting permission to implement):**
1. The tool stores the plan's content as `Task.currentPlan`, `Task.status = planReady`.
2. The tool **blocks**, subscribing to `watchPlanDecision(taskId)`.
3. The panel shows the plan with two actions:
   - **Approve** → `approvePlan(taskId)` → the tool grants Claude Code permission to exit plan mode → `Task.status → running`, the execution phase starts (§6.2).
   - **Feedback** → `submitPlanFeedback(taskId, message)` → creates a new `TaskFeedback` (`phase = plan`; the same entity as post-PR feedback — semantically it's always "a message from the dev to the agent within the same session," the `phase` field distinguishes them in the history) → the tool denies the exit, returning the feedback text as the reason → Claude plans again, `Task.status` goes back to `planning`, the loop repeats until approval.

This is deliberately more work than a simple fallback (auto-rejecting both calls via `--permission-prompts none`), but it's one of the things that genuinely differentiates the product — we're doing it properly from the start.

### 6.5 Access to private repositories

The agent needs to be able to clone and push changes to a repo that may be private. Three options, from simplest to most "production-grade":

**Option 1 — Personal Access Token, fine-grained (recommended for Must)**
When creating a `Project`, the dev pastes a GitHub *fine-grained* PAT, manually generated in GitHub's settings, scoped to a single repo, with `Contents: Read and write` permissions (and `Pull requests: Write`, if the agent should open the PR itself via the GitHub API instead of just pushing the branch). Advantages: no GitHub API integration beyond just using the token, works over plain HTTPS (`https://x-access-token:<token>@github.com/org/repo.git`), nothing to install on the agent's side. We store the token as `Project.repoAccessToken`, `scope=serverOnly` — it never reaches the panel. The server hands the token to the agent only at the moment a specific task starts (as a call parameter), the agent injects it into the clone URL and **never persists it to disk**.

**Option 2 — Deploy key (SSH) per project (alternative, similar cost)**
The server generates an SSH key pair when the project is created, the public key is shown to the dev to paste into GitHub → Settings → Deploy keys (with "Allow write access" enabled). The private key is stored encrypted server-side, handed to the agent analogously to option 1. Plus: the token has no access to anything beyond a single repo by definition (no need to manually police the scope like with a PAT). Minus: a bit more work (keygen, `GIT_SSH_COMMAND`, `known_hosts`).

**Option 3 — GitHub App (Could / production)**
Registering our own GitHub App, the dev installs it on selected repos, the server exchanges a JWT for a short-lived installation token per repo. The most secure and "professional" solution (tokens expire automatically, no manually pasted secrets), but requires registering an app with GitHub, handling token exchange and webhooks — realistically a separate epic, not worth it alongside the rest of the scope in 5 weeks.

**Recommendation:** Option 1 for Must. Important security caveat to handle before the demo: `scope=serverOnly` protects the field from leaking through the Serverpod API, but that's not the same as encryption at rest — the token sits in Postgres as plain text. That's an acceptable risk for the hackathon (a local database in docker-compose), but it's worth naming clearly in the README as a "known limitation" rather than staying silent about it — judges tend to appreciate awareness of a limitation more than its absence.

#### 6.5.1 In-panel help for the token field

A fine-grained PAT is something most developers haven't heard of yet (we found that out ourselves) — the field itself needs to explain itself, or the dev gets stuck at the very first onboarding step. Solution: a short, always-visible description under the field + an expandable "How do I do this?" with abbreviated steps, instead of only linking out to GitHub's external documentation.

**Text always visible under the field:**
> A fine-grained token with *Contents: Read and write* permission, scoped to this repository. [How do I do this? ▸]

**Content once expanded:**
1. GitHub → profile → **Settings** → **Developer settings** → **Personal access tokens** → **Fine-grained tokens**
2. **Generate new token** — pick the *Resource owner* (yourself, or the organization if the repo lives there)
3. **Repository access** → *Only select repositories* → pick this one repo
4. **Permissions** → *Contents: Read and write* (add *Pull requests: Write* if the agent should open PRs itself)
5. **Generate token** and paste it here — GitHub only shows it once

**Note for a repo inside an organization:**
> If the repo belongs to an organization, pick it as the *Resource owner*. Don't see it in the list? Ask an admin to enable fine-grained tokens in the organization's settings — the token may also require their approval.

**Additional UX elements:**
- A direct shortcut link to the generator: `https://github.com/settings/personal-access-tokens/new` (saves clicking through menus)
- An expiration hint: *"The token will expire after at most 366 days — it's worth setting yourself a reminder to renew it."*
- A backup link to GitHub's official documentation, in case the above isn't enough

This is a great candidate for a shared component (`TokenHelpTooltip` / accordion), because the exact same content will also be useful in the repo's README — one source of text, two places it's shown.

### 6.6 Agent roles and prompt context

A role is an enum (`AgentRole`) + a static prompt prefix prepended to the task content. No AI, no routing — a plain string template:

```dart
const rolePrompts = {
  AgentRole.frontend: "You are {name}, the frontend specialist on this team. "
      "Focus on UI, components, styling and client-side logic.",
  AgentRole.backend: "You are {name}, the backend specialist. "
      "Focus on API design, data models and server-side logic.",
  AgentRole.devops: "You are {name}, the DevOps specialist. "
      "Focus on deployment, CI/CD and infrastructure configuration.",
  AgentRole.fullstack: "You are {name}, a fullstack generalist on this team.",
  AgentRole.generalist: "You are {name}, a generalist engineer on this team.",
};
```

Deliberately **without** hard permission restrictions per role (e.g. blocking a frontend agent from touching the backend) — that would require sandboxing at the filesystem/permissions level, disproportionate to the value for a hackathon. A role is context, not a restriction.

**Default model and effort per agent** (`Agent.defaultModel`, `Agent.defaultEffort`) is a second, independent axis of personalization — not tied rigidly to the role. Example: Adam (code review/audit) gets a stronger model and higher effort, because accuracy matters more than speed here; Ana (development, lots of small tasks) gets a cheaper/faster model. Both fields are optional — `null` means "leave Claude Code's defaults." The flags are appended to the command from §6.2 only when set.

### 6.7 Viewing the diff and full file content in the panel

A diff is **not** something you need to compute yourself — GitHub has already computed it. Rather than fetching the whole PR diff as one block of text, it's better to build the view around the list of changed files.

**Important: these GitHub API calls are made by the server, never the panel.** `repoAccessToken` has `scope=serverOnly` — it cannot reach the client. The panel calls an ordinary Serverpod endpoint, and the server internally (having access to the token) queries GitHub and returns the already-parsed result:

```dart
class TaskEndpoint extends Endpoint {
  Future<List<DiffFile>> getChangedFiles(Session session, int taskId) async {
    // GET https://api.github.com/repos/{owner}/{repo}/pulls/{number}/files
    // Authorization: Bearer <repoAccessToken> — token read server-side, never sent to the panel
  }

  Future<String> getFileContent(Session session, int taskId, String contentsUrl) async {
    // GET {contentsUrl}, Accept: application/vnd.github.raw — same as above
  }
}
```

Each entry from `getChangedFiles` comes with ready-to-use fields: `filename`, `status` (added/modified/removed), `additions`, `deletions`, `patch` (the diff for *that one file*), and `contentsUrl` — a link to fetch the file's full content at that version, passed on to `getFileContent`. This lets the panel show a list of changed files with a `+X -Y` counter, and on click, the diff for a specific file, without downloading and parsing one giant blob at once.

**"View full file"** is a call to `getFileContent`, which internally makes a second request to the same `contentsUrl`, only with a different `Accept` header that returns plain text instead of a JSON object with base64.

Rendering the diff and the full file comes down to splitting the text into lines and (for the diff) coloring by the leading character (`+`/`-`) — no diffing algorithm of our own. None of this is stored in the database: it's fetched on demand, when the dev opens the task view while it's in the `awaitingReview` state.

A limitation worth noting: the Contents API only returns content directly for files up to ~1 MB — larger ones need the separate Git Blobs API. Negligible for the hackathon.

Next to the rendered diff there's always an "Open in GitHub" link (`prUrl`) — for a dev who wants to do a full code review with inline comments. We deliberately don't rebuild that in our own UI (see Won't).

### 6.8 Agent (daemon) install and uninstall handshake

**Registration:**
1. The dev clicks "Add machine" in the panel, names it → the panel generates a one-time registration token and shows the ready-to-run command:
   ```
   ./scripts/install-agent.sh --token <TOKEN> --server https://your-server.example.com
   ```
2. The dev clones the repo on the target machine and runs this command.
3. The script installs the daemon binary as a systemd service. The token goes **not** into the unit file itself (so it isn't visible via `systemctl status`/`ps`), but into a separate config file with restrictive permissions (`/etc/agent-runner/config.env`, `chmod 600`).
4. `systemctl daemon-reload && systemctl enable --now agent-runner` — the daemon starts, connects outbound, the server verifies the token hash, `Machine.status → online`, `lastSeenAt` starts updating.
5. Creating further agents on this machine (name + role) is from this point a plain database write — nothing else needs to be installed.

**Deleting a machine — two guards, not one:** besides non-terminal tasks (already described in §5), deleting a `Machine` is blocked while `status == online` — the daemon is still alive and connected, deleting the record out from under it would leave a process on the VPS sending a heartbeat into the void. Clicking "Delete" on a machine in this state **doesn't show a plain error**, but immediately shows the ready-to-run uninstall command (the same one from the step below), so the dev can properly shut the machine down right away instead of guessing what to do next. A note in the same dialog: *"If this machine no longer physically exists, you don't need to do anything — the status will switch to offline on its own within ~60s once the heartbeat stops arriving."* — without this, a dev could think they're stuck forever.

**Detecting that a machine has died:** the heartbeat alone (updating `lastSeenAt`) isn't enough — if it stops arriving, nothing gets written to the database, so `Model.db.watch()` never fires (it reacts to writes, not to the passage of time). A periodic **Future Call** in Serverpod is also needed (a built-in background job mechanism): e.g. every 30s it goes through all machines and if `lastSeenAt` is older than the threshold (e.g. 60s), it sets `status = offline` itself. Only that write actually "wakes" the panel via the stream.

**What happens to tasks the daemon on the dead machine was running?** The same Future Call marks all non-terminal tasks (`planning`, `waitingForAnswer`, `planReady`, `running`) of that machine's agents as `failed`, with `failureReason = "Machine went offline mid-task"`. They deliberately **don't** automatically go back into a queue — `claudeSessionId` lives locally on that specific machine's disk, so it can't be resumed elsewhere. When the machine comes back online, it's the dev who decides whether to create a new task from scratch, not the system automatically.

**Uninstalling:** the uninstall script doesn't just stop the service locally (`systemctl disable --now`, removing the unit and config), it **also** calls the server one last time before closing the connection, so the server can immediately revoke the token and set `Machine.status = offline` (a deliberate deregistration, not waiting for the heartbeat timeout) — otherwise the server only finds out after 60s. This **doesn't delete** the `Machine` record from the database — the deletion itself is a separate, deliberate step the dev takes in the panel, now unblocked since the status is already `offline`.

**Deliberately accepted limitation:** if two agents on the same machine get tasks at the same time, the daemon launches two Claude Code subprocesses at once — no concurrency limit. Fine for the hackathon; "max concurrent tasks per machine" is a good Could candidate if a demo on a weaker VPS starts choking.

### 6.9 Machine metrics (CPU / RAM)

Alongside handling tasks, the daemon periodically (e.g. every 5-10s) collects local system metrics. On Linux this is the cheapest possible implementation — reading `/proc/stat` (CPU) and `/proc/meminfo` (RAM), with no external dependencies, consistent with the earlier decision to focus on Linux.

Each reading is sent to the server as an ordinary method call (`machineEndpoint.reportMetric(machineId, cpuPercent, memUsedMb, memTotalMb)`), which stores a new `MachineMetric` row.

**Snapshot (Should):** the panel shows the latest reading per machine — a simple `watch` on the latest row, done.

**Real-time chart (Could):** requires keeping a short window of history, not just the last value. Two extra things to handle that a plain snapshot doesn't need:
- **Retention:** without cleanup the table grows without bound (a sample every 5s = ~17k rows/day/machine). Another periodic Future Call deletes rows older than, say, 30 minutes — older history isn't needed for a "live" chart anyway.
- **A window stream, not a single row:** the endpoint can't just do `MachineMetric.db.watch()` on one record (every reading is a new row, not an update to an existing one) — on each new entry it has to re-read the last N samples and send the whole, sliding list to the client. That's a bit more work than the streams elsewhere in this project so far, hence Could, not Must/Should.

Recommendation: start with the snapshot (cheap, looks good in the demo as a "live" number in the corner of the machine card), only build the historical chart if the rest of Must/Should is already done.

### 6.10 Execution isolation: git worktree (MVP) and docker mode (Should/Could)

**Problem:** with a shared `~/projects/<repo>` folder per machine, two agents (or even the same agent on two tasks) working on the same project at the same time collide over the working directory — two simultaneous `git checkout`s to different branches in one directory can't coexist.

**MVP solution — git worktree, fully native, no Docker:**

The daemon keeps **one bare clone per project** (just git history/objects, no working directory) and, when each task starts, runs:

```bash
git worktree add worktrees/<taskId> -b task-<taskId>
```

Every task gets its own, fully independent working directory and branch, but all worktrees share the same git objects on disk — a cheap, native git mechanism, not a full re-clone every time.

- **Feedback = the same worktree.** Another iteration of the same task (via `--resume`) goes back to the existing worktree rather than creating a new one.
- **Cleanup:** once a task reaches a terminal state (`done`/`failed`/`cancelled`), the daemon removes the worktree (`git worktree remove`) — the exact timing/retention window is a minor implementation detail, not an architectural one.

This solves the concurrency problem **without** Docker — worktrees remain the foundation even once we add `docker` mode later (a container mounts the worktree as a volume, it doesn't replace it).

**`docker` mode (Should/Could) — not every agent should be isolated the same way:**

An agent editing code in a repo genuinely benefits from isolation (different Node/toolchain versions between projects, a safety boundary). But an infrastructure-maintenance agent (e.g. changing an nginx config, restarting system services) by definition **needs** access to the real host — locking it in a container would defeat the purpose of its existence. That's why execution mode is a **property of a specific agent** (`Agent.executionMode`), not a global architectural decision:

| | `native` | `docker` |
|---|---|---|
| When to use | an infrastructure agent (nginx, systemd, packages) | a coding agent (frontend/backend/fullstack) |
| Access | full host | only the mounted worktree for that task |
| Default | opt-in (a deliberate choice) | eventually, yes |

The `Project.dockerImage` field lets a project specify its own base image (e.g. `node:20-bookworm` + a preinstalled `claude` CLI + git); without it, a sensible default image.

**Scope for the hackathon:** the schema (`AgentExecutionMode`, `dockerImage`) is ready right now, but **the only implemented mode for Must is `native`** — worktrees solve the most urgent problem (concurrency) without extra infrastructure. `docker` means adding another branch in the daemon later, not rewriting the schema.

**Deliberately out of scope:** an "infrastructure" agent (nginx config, restarting services) is a completely different shape of task than "edit code in a repo" — the current `Task` model assumes a repo/branch/PR everywhere. That kind of agent is a separate future epic (a different task shape, no PR), not something to force into the current model for the hackathon.

### 6.11 Claude Code authorization on the agent's machine

We're assuming a Pro/Max subscription (not API billing) — Claude Code has a dedicated bootstrapping path for this, with no need for a browser on the machine itself:

```bash
claude setup-token
```

The command prints a URL, the dev opens it in any browser (e.g. on their laptop — it doesn't need to be a GUI on the VPS), logs in there, and a **long-lived OAuth token** (`CLAUDE_CODE_OAUTH_TOKEN`) comes back to the terminal on the machine, billed against the Pro/Max subscription.

**Why `setup-token` and not plain `claude login` directly on the VPS:** some VPS providers (e.g. Hetzner) have Cloudflare protection that blocks a direct OAuth redirect performed from the server itself (`claude login` on the VPS gets a 403). `setup-token` avoids this — the browser step happens off the machine.

The token goes into the same config file as the machine's registration token (`/etc/agent-runner/config.env`, see §6.8), the daemon reads it from the local environment when launching the subprocess:

```bash
CLAUDE_CODE_OAUTH_TOKEN=<token> claude -p "..." --output-format stream-json ...
```

**Important: this token never reaches the central server or the database.** Unlike `repoAccessToken` (which the server distributes to whichever machine is running a given project), this token is tied to a specific `claude` installation on a specific host — it stays local.

**`docker` mode:** this is just passing the same environment variable through to the container at runtime (`docker run -e CLAUDE_CODE_OAUTH_TOKEN=...`) — no login inside the image, no secrets baked into it.

**Deliberate limitation worth writing into the README:** the token is pinned to one human subscription, with usage limits designed for one person's interactive work. Several agents firing off subprocesses concurrently on the same token will hit Pro/Max limits sooner than a single developer working by hand — not something to solve now, but worth naming explicitly so no one is surprised during a demo with several agents running in parallel.

### 6.12 Demo seed data and judge setup

`docker compose up` brings up the server, the database, and one registered agent locally — but the stack on its own **won't show the full live flow** without two things we can't provide on the judge's behalf:

- **`CLAUDE_CODE_OAUTH_TOKEN`** — that's a personal subscription, we can't (and shouldn't) include our own — it's an account secret. The README must explicitly ask the judge to run `claude setup-token` and paste it into `.env` before starting.
- **Repo access** — to minimize friction, we include the team's own public demo repo (a simple React todo app) with a ready-made, narrowly-scoped fine-grained PAT in `.env.example`, so the judge doesn't need to set up their own repo just to test the project. On first start, the panel already has a seeded `Project` pointing at it.

README: a short "before you run this" checklist (paste the Claude Code token → `docker compose up` → done, a task can be created right away on the seeded project). This settles the earlier open question of "exactly what does the judge need to configure to see a working loop."
